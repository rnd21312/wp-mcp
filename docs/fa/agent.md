# ایجنت هاست (نسخه ۲)

ایجنت هاست یک برنامه‌ی کوچک PHP است که روی هاست شما قرار می‌گیرد و به Studio (روی کامپیوتر شما) اجازه می‌دهد سایت را از صفر بسازد و منتشر کند، با امنیت بالا. فقط **PHP 8.1 به بالا** و HTTPS لازم است؛ Node، شل یا دیتابیس برای خودِ ایجنت لازم نیست.

## نصب در پنج قدم

۱. در Studio به **هاست‌ها ← دانلود ایجنت** بروید. زیپ یک **کد نصب** یک‌بار‌مصرف دارد (در Studio نمایش داده می‌شود).
۲. زیپ را روی هاست آپلود و Extract کنید (فایل‌منیجر ← Upload ← Extract) کنار فایل‌های سایت، مثلاً داخل `public_html`. پوشه‌ی `wpm-agent` ساخته می‌شود.
۳. `https://دامنه‌ی-شما/wpm-agent/` را باز کنید. ویزارد هاست را بررسی می‌کند و کد نصب، نام کاربری و گذرواژه (حداقل ۱۰ نویسه) می‌خواهد. تأیید دو مرحله‌ای را در صفحه‌ی **امنیت** روشن کنید.
۴. در ایجنت **ساخت کد اتصال** را بزنید (۱۰ دقیقه معتبر).
۵. در Studio: **هاست‌ها ← اتصال هاست**، نشانی و کد را وارد کنید. Studio یک کلید امضا نگه می‌دارد و چیز دیگری ذخیره نمی‌شود.

زیپ عمومی `dist/wpm-agent.zip` (`npm run package:agent`) هم کار می‌کند؛ در این حالت ویزارد مسیر فایلی را نشان می‌دهد که کد نصب در آن است و آن را در فایل‌منیجر باز می‌کنید.

## انتشار سایت

**پروژه‌ها ← پروژه‌ی جدید** یک پوشه روی کامپیوتر شما می‌سازد (ایستا یا اپ تک‌صفحه‌ای). فایل‌ها را در Studio (یا هر ویرایشگر) ویرایش کنید و **همین حالا منتشر کن** را بزنید. اولین انتشار سایت را روی هاست می‌سازد و بعدی‌ها نسخه‌ی تازه اضافه می‌کنند. **هاست‌ها ← سایت‌ها و نسخه‌ها** نسخه‌ها را نشان می‌دهد و با یک کلیک برمی‌گرداند. پنل خودِ ایجنت هم همین را دارد: آپلود زیپ از مرورگر، فهرست نسخه‌ها، بازگشت.

اپ‌های تک‌صفحه‌ای (React، Vue، Svelte با Vite و …): پوشه‌ی ساخت را منتشر کنید (اگر `dist/index.html` باشد خودکار استفاده می‌شود)؛ ایجنت قواعد بازنویسی را برای Apache/LiteSpeed اضافه می‌کند. روی nginx این خط را بگذارید: `try_files $uri /index.html;`.

## انتشار چگونه کار می‌کند

```
زیپ (Studio) ← تکه‌هایی متناسب با post_max_size هاست ← بررسی sha256 روی هاست
← باز کردن در releases/<id> (با اعتبارسنجی) ← سوییچ ← نگه‌داشتن ۵ نسخه‌ی آخر
```

* **حالت symlink** (VPS یا هاستی که symlink مجاز است، پوشه‌ی جدید یا خالی): پوشه‌ی زنده یک symlink به نسخه است و سوییچ یک rename اتمیک است.
* **حالت sync** (همه‌ی هاست‌های اشتراکی، یا وقتی پوشه از قبل فایل دارد): فایل‌های نسخه‌ی جدید کنار نام نهایی نوشته و جابه‌جا می‌شوند (HTML آخر)؛ فایل‌هایی که فقط نسخه‌ی قبل داشت حذف می‌شوند. **فایل‌هایی که ایجنت نگذاشته هرگز پاک نمی‌شوند** و آنچه باید بازنویسی شود اول در `backups/<نسخه>/` کپی می‌شود.
* بازگشت همان سوییچ به نسخه‌ی قدیمی‌تر است. نسخه‌ها تغییرناپذیرند.

## مدل امنیتی

| نگرانی | اقدام |
|---|---|
| چه کسی نصب می‌کند | کد نصب که فقط صاحب زیپ/دسترسی فایل می‌داند؛ حدس غلط محدود می‌شود؛ فایل کد بعد از نصب پاک می‌شود |
| گذرواژه | argon2id (یا bcrypt) روی پیش‌هش SHA-256؛ حداقل ۱۰ نویسه، گذرواژه‌های رایج رد می‌شوند |
| حمله‌ی حدسی | ۵ شکست کاربر و آدرس را ۱۵ دقیقه قفل می‌کند و تا ۲۴ ساعت دو برابر می‌شود؛ قفل برای گذرواژه‌ی درست هم هست |
| دو مرحله‌ای | TOTP (RFC 6238 با بردارهای استاندارد آزمایش شده)؛ هر کد یک بار |
| نشست‌ها | شناسه‌ی تصادفی (هش‌شده)، HttpOnly، SameSite=Strict، Secure روی HTTPS، ۲ ساعت بیکاری / ۱۲ ساعت مطلق، توکن CSRF و بررسی Origin |
| انتقال | ورود، نصب و API فقط با HTTPS؛ HTTP فقط از loopback یا وقتی مالک در نصب صریحاً ریسک را بپذیرد |
| درخواست‌های Studio | HMAC-SHA256 روی زمان، nonce، کلید، متد، مسیر و هش بدنه (هم‌قالب با بریج وردپرس)؛ پنجره‌ی ۵ دقیقه؛ هر nonce یک بار؛ پاسخ‌ها امضا می‌شوند؛ امضای غلط مکرر آدرس را قفل می‌کند |
| سطوح | اتصال‌ها `read`، `deploy` یا `admin`؛ ساخت/حذف سایت `admin` می‌خواهد؛ کد اتصال یک‌بار‌مصرف و ۱۰ دقیقه‌ای؛ اتصال قابل لغو |
| فایل‌ها | هر مسیر بیرونی اعتبارسنجی می‌شود (بدون `..`، مطلق، درایو، بک‌اسلش، کنترل‌کاراکتر، فرار با symlink)؛ سایت‌ها فقط در ریشه‌های مجاز و هرگز داخل پوشه‌ی ایجنت/داده |
| آرشیو | zip-slip، zip-bomb (حد حجم، نسبت و تعداد هنگام باز کردن)، CRC، لینک و فایل ویژه رد می‌شوند؛ سایت ایستا/SPA فایل اجرایی و تنظیمات سرور را رد می‌کند (`.php`، `.htaccess`، `web.config`، `.env`، `.git` …) |
| دستورها | ایجنت هرگز از ورودی دستور شل نمی‌سازد. تنها دستور ممکن `node -v` ثابت برای گزارش قابلیت است |
| داده | فایل‌های JSON با خط محافظ PHP، در پوشه‌ی بیرون از وب‌روت (در صورت امکان) یا با قوانین deny؛ دسترسی 0600 |
| ممیزی | گزارش افزودنی از ورودها، شکست‌ها، اتصال‌ها، تغییر سایت، انتشار و بازگشت |

محدودیت‌های صادقانه: برای تأیید درخواست‌ها، کلید امضا باید روی هاست ذخیره شود؛ پس کسی که پوشه‌ی داده را بخواند می‌تواند خود را Studio جا بزند (لغو و اتصال دوباره). اتصال `admin` در مراحل بعد می‌تواند سایت سمت‌سرور بسازد که طبیعتاً اجرای کد دارد؛ سایت ایستا/SPA چنین نیست. ایجنت نمی‌تواند از هاستِ از قبل نفوذشده محافظت کند.

## چه چیزهایی را تشخیص می‌دهد

صفحه‌ی هاست‌ها: نسخه و افزونه‌های PHP، محدودیت آپلود/حافظه و اندازه‌ی تکه، وب‌سرور، پنل هاست (cPanel، DirectAdmin، Plesk، CyberPanel، CloudPanel، Hestia)، پشتیبانی symlink، فضای آزاد، بیرون بودن پوشه‌ی داده از وب‌روت و وجود Node. مراحل بعد از اینها برای ساخت دیتابیس و اجرای اپ‌های سمت‌سرور استفاده می‌کنند.

## سایت وردپرس جدید (M2)

**هاست‌ها ← سایت وردپرس جدید.** Studio جای سایت را می‌سازد و ایجنت: (۱) دیتابیس می‌سازد، (۲) `latest.zip` رسمی را دانلود و با SHA-1 منتشرشده‌ی wordpress.org تطبیق می‌دهد، (۳) باز می‌کند، `wp-config.php` با saltهای تازه و پیشوند جدول تصادفی می‌نویسد، (۴) افزونه‌ی بریج را کپی می‌کند. سپس Studio نصب‌کننده‌ی خود وردپرس را از راه HTTP اجرا می‌کند، ایجنت بریج را فعال و برایش کد جفت‌سازی می‌سازد و Studio خودکار جفت می‌شود. نشانی مدیریت، نام کاربری و گذرواژه‌ی تولیدشده فقط یک بار نشان داده می‌شود و Studio ذخیره‌اش نمی‌کند.

دیتابیس (در پنجره انتخاب می‌کنید):

| روش | چگونه |
|---|---|
| cPanel | UAPI با API token (پورت ۲۰۸۳): ساخت دیتابیس، کاربر و دسترسی |
| DirectAdmin | `CMD_API_DATABASES` با Login Key (پورت ۲۲۲۲) |
| مدیر MySQL (VPS) | ایجنت با اطلاعات root وصل می‌شود و خودش دیتابیس، کاربر و دسترسی می‌سازد |
| مشخصات را دارم | نام، کاربر و گذرواژه را می‌دهید؛ اتصال قبل از هر نوشتنی آزمایش می‌شود |

توکن پنل و گذرواژه‌ها یک بار از کانال امضاشده می‌روند و ذخیره نمی‌شوند. گذرواژه‌ی دیتابیس جدید روی هاست تولید و فقط در `wp-config.php` نوشته می‌شود. اگر ساخت دیتابیس شکست بخورد هیچ فایلی دانلود یا نوشته نمی‌شود؛ checksum نادرست یعنی نصب نمی‌شود.

هنوز نیست: API پلسک، SQLite برای وردپرس، نصب MySQL روی VPS خام (مسیر تأییدشده و فهرست‌سفید در M4) و حالتی که نصب‌کننده‌ی وب از کامپیوتر شما در دسترس نیست (در این حالت خودتان `wp-admin/install.php` را باز می‌کنید؛ فایل‌ها و دیتابیس آماده‌اند).

## وضعیت

مرحله‌ی M1: نصب‌کننده، احراز هویت، API امضاشده، آپلود تکه‌ای، نسخه‌ها، سوییچ اتمیک، بازگشت، انتشار ایستا و SPA. حالت symlink فقط روی هاست‌هایی که symlink دارند با تست واحد پوشش داده می‌شود (روی ویندوز توسعه نه)؛ حالت sync سرتاسری آزموده شده. بعدی: راه‌اندازی وردپرس (ساخت دیتابیس با API پنل‌ها یا خود ایجنت)، [v2-plan.md](../v2-plan.md).
