# مدل امنیتی

## به چه کسی اعتماد می‌شود

* **مالک** (یک نفر برای هر gateway) با رمز وارد `/admin` می‌شود، کلید API می‌سازد، اپ‌های OAuth را تأیید می‌کند و سایت‌ها را وصل می‌کند.
* **یک اتصال** (کلید API یا اپ OAuth) با یک *سطح* روی چند *سایت* کار می‌کند و فقط تا همان سطح مورد اعتماد است.
* **مدیر وردپرس** که کد جفت‌سازی را می‌سازد، حسابی است که افزونه روی آن سایت به‌جایش عمل می‌کند.
* **محتوای وب‌سایت** (نوشته، نظر، ورودی فرم، مقدار گزینه، عنوان) *قابل‌اعتماد نیست*: غریبه‌ها می‌توانند آن را بنویسند.

## سطح‌ها

| سطح | اجازه می‌دهد | نمونه |
|---|---|---|
| `read` | داده‌ی منتشرشده و غیرحساس | محتوا و دسته‌های منتشرشده، توکن‌های طراحی، CSS، منو، فیلدهای سئو، HTML رندرشده، ممیزی صفحه، فعالیت |
| `draft` | + پیش‌نویس، محتوای خصوصی، آپلود، متن نظرات، فهرست افزونه‌ها، سلامت، بررسی به‌روزرسانی، نسخه‌ها | ذخیره‌ی پیش‌نویس، آپلود رسانه، سئوی پیش‌نویس‌ها، کشف REST |
| `live` | + هرچه بازدیدکننده می‌بیند | انتشار/ویرایش منتشرشده‌ها، قالب‌ها، CSS، توکن‌ها، منو، ریدایرکت، محصول/موجودی/کوپن، مدیریت نظرات، کش، فرم‌ها، undo |
| `admin` | + هر چیز حساس | افزونه‌ها، به‌روزرسانی، بکاپ/بازگردانی، کاربران، گزینه‌ها، سفارش‌ها، پاکسازی دیتابیس، جستجو-جایگزینی، فایل‌های پوسته، لاگ‌ها، هر مسیر REST فهرست‌نشده |

سطح مؤثر = `min(سطح اتصال، سقف سایت)`. سقف هم در gateway و **هم** داخل وردپرس (*ابزارها ← WP MCP Bridge*) تعیین می‌شود و افزونه هر فراخوانی را دوباره می‌سنجد؛ پس gateway هک‌شده هم از چیزی که صاحب سایت اجازه داده فراتر نمی‌رود. بعضی عملیات از روی هدف واقعی *بالا می‌روند* (ویرایش نوشته‌ی منتشرشده `live` می‌خواهد؛ تغییر نمایش سایت در موتورهای جستجو `admin`).

آنچه `read` عمداً نمی‌بیند: پیش‌نویس‌ها و نوشته‌های خصوصی، کاربران (فقط نام عمومی نویسنده‌ها)، سفارش‌ها و مشتریان، گزینه‌هایی جز تنظیمات عمومی، ایمیل/IP نظرات، لاگ‌ها، نسخه‌ی افزونه‌ها، ورودی فرم‌ها، بکاپ‌ها. مقدار گزینه یا متایی که کلیدش شبیه رمز است (`*secret*`، `*token*`، `*password*`، `*api_key*`، `*license*`، `*smtp*`…) هرگز برنگردانده می‌شود، حتی برای admin، و نوشتنی هم نیست.

## تأیید، بازگردانی، فعالیت

* عملیات علامت‌خورده **confirm** (حذف دائمی، نصب افزونه/پوسته، دریافت از URL، به‌روزرسانی، بازگردانی، جستجو-جایگزینی با apply، نوشتن فایل پوسته، تغییر نقش…) اول پیش‌نمایش و `confirm_token` برمی‌گردانند. توکن امضاشده، ۵ دقیقه معتبر و وابسته به اتصال، سایت، عملیات **و دقیقاً همان آرگومان‌هاست**. این سد در برابر اشتباه و حلقه‌ی بی‌پایان است؛ به هوش مصنوعی گفته می‌شود پیش‌نمایش را به کاربر نشان دهد و منتظر «بله» بماند. به‌خودیِ‌خود ثابت نمی‌کند انسانی «بله» گفته: برای آن از تأیید ابزار خود کلاینت MCP استفاده کنید و سطح‌های بالا را برای نشست‌های زیرنظر نگه دارید.
* هر نوشتن یک snapshot قبلی ثبت می‌کند. `activity.undo {revision}` نوشته‌ها (فیلد، متا، دسته‌ها)، گزینه‌ها و تنظیمات، CSS، توکن‌ها، منو، ریدایرکت، فعال‌بودن افزونه، پوسته، وضعیت نظرات و فایل‌های پوسته را برمی‌گرداند. برگشت‌ناپذیر: حذف دائمی، حذف افزونه، پاکسازی/بهینه‌سازی دیتابیس، جستجو-جایگزینی، به‌روزرسانی‌ها، حذف کاربر. `maintain.update` اول بکاپ دیتابیس می‌گیرد و `maintain.backup_restore` قبل از بازگردانی بکاپ ایمنی می‌سازد.
* gateway هر فراخوانی را لاگ می‌کند (چه کسی، سایت، عملیات، نتیجه، خلاصه‌ی کوتاه آرگومان) و افزونه هم (نوشتن‌ها و خطاها). هوش مصنوعی با `activity.log` و `activity.list` هر دو را می‌خواند؛ مالک در پنل و در *ابزارها ← WP MCP Bridge* می‌بیند.

## دفاع شبکه‌ای

* **gateway ← سایت**: HTTPS؛ پاسخ DNS **در لحظه‌ی اتصال** بررسی می‌شود و بازه‌های خصوصی، loopback، link-local، metadata (169.254.x)، CGNAT، multicast و رزرو شده رد می‌شوند (جلوی rebinding)؛ redirect هرگز دنبال نمی‌شود؛ حجم پاسخ و زمان محدود است. سایت محلی/خصوصی پرچم صریح توسعه می‌خواهد.
* **دانلودهای افزونه** (`media.import_url`، `plugins.install_zip`): فقط https، بدون credentials، بدون redirect، همه‌ی آدرس‌های resolve‌شده باید عمومی باشند، سقف حجم و بررسی واقعی نوع فایل. `install_zip` هم admin است هم confirm. افزونه میزبان را پیش از دریافت resolve می‌کند؛ rebindingِ فوق‌سریع بین بررسی و دریافت ریسک نظریِ باقی‌مانده است و به همین دلیل نصب از URL فقط admin است.
* **امضای درخواست**: HMAC-SHA256 روی زمان، nonce، شناسه‌ی کلید، مسیر و هش بدنه؛ ±۵ دقیقه؛ حافظه‌ی ضد replay؛ پاسخ هم امضا می‌شود و gateway پاسخ بی‌امضا را رد می‌کند.
* **جفت‌سازی**: کد یک‌بارمصرف (۸۰ بیت)، ۱۵ دقیقه، ۵ اشتباه آن را می‌سوزاند، روی http ساده رد می‌شود، rate limit برای هر آدرس. secret سایت یک بار به gateway داده و آنجا با AES-256-GCM رمز ذخیره می‌شود.
* ابزارهای **inspect** فقط صفحه‌های خود همان سایت را می‌گیرند.

## OAuth

* کد مجوز + **فقط PKCE S256**، فقط کلاینت عمومی، کدهای یک‌بارمصرف (۶۰ ثانیه).
* ثبت پویا مجاز است (Claude.ai لازم دارد) ولی محدود: ۱ تا ۵ redirect که باید `https`، `http` روی loopback (ابزارهای دسکتاپ) یا scheme ویرایشگر باشند؛ بدون fragment، credentials، `javascript:`/`data:`؛ حداکثر ۲۰۰ ثبت؛ ۱۰ در ساعت برای هر آدرس؛ ثبت‌های بی‌استفاده بعد از یک روز پاک می‌شوند.
* صفحه‌ی تأیید session مالک می‌خواهد، نام خودِ‌اعلام‌شده‌ی اپ را با یادداشت «تأییدنشده»، **دامنه‌ی redirect را درشت**، انتخاب سطح (`admin` هرگز از پیش انتخاب نمی‌شود) و تیک سایت‌ها را نشان می‌دهد و CSRF دارد.
* توکن دسترسی ۱ ساعت؛ refresh token ۱۸۰ روز لغزان و چرخشی؛ استفاده‌ی دوباره از توکن قدیمی بعد از پنجره‌ی ۱۰ دقیقه‌ای زنجیره را باطل می‌کند. توکن‌ها فقط به‌صورت هش SHA-256 ذخیره می‌شوند. grant *فعلی* مالک در هر فراخوانی خوانده می‌شود، پس پایین‌آوردن سطح یا قطع اپ فوری است.
* endpoint توکن برای هر کلاینت rate limit دارد و تلاش‌های ناموفق Bearer برای هر آدرس کند می‌شود.

## تزریق دستور (Prompt injection)

متنی که از وب‌سایت می‌آید با `content_notice` برمی‌گردد و `instructions` سرور به مدل می‌گوید آن را داده بداند. این توصیه به مدل است نه اجبار. اجبار ساختاری است: مدلی که نظر مخرب را بخواند هم از سطح خود بیشتر نمی‌تواند، باز به مرحله‌ی تأیید عملیات مخرب می‌خورد، قابل برگشت است و در لاگ دیده می‌شود. پایین‌تر از `admin`، HTML نوشته‌شده با `kses` فیلتر می‌شود (بدون اسکریپت)؛ CSS مواردی چون `</style>`، `javascript:`، `expression()` و `@import` راه‌دور (جز Google Fonts) را رد می‌کند.

## پنل محلی (بدون رمز)

`wp-mcp local` یک پنل تک‌صفحه‌ای بدون ورود ارائه می‌دهد، پس نباید جز شما کسی به آن برسد. فقط روی `127.0.0.1` گوش می‌دهد. هر درخواست باید `Host` محلی داشته باشد (صفحه‌ی وبی که با DNS rebinding برسد Host دیگری می‌فرستد و رد می‌شود)، اگر `Origin` هست باید همان origin باشد و هدر اختصاصی `X-WPM-Panel` را داشته باشد (صفحه‌ی بیگانه بدون preflight نمی‌تواند آن را اضافه کند و پنل هیچ‌وقت preflight را نمی‌پذیرد). پنل محلی را پشت پروکسی معکوس یا تونل نگذارید؛ برای آن از gateway معمولی با رمزش استفاده کنید. هر کس بتواند در ویندوزِ شما مرورگر را استفاده کند می‌تواند پنل را هم استفاده کند، مثل هر ابزار محلی دیگر.

## پنل مالک

رمز با scrypt هش می‌شود، کوکی امضاشده‌ی `HttpOnly` و `SameSite=Lax` (روی https `Secure`)، توکن CSRF در هر فرم، کند‌کردن ورود، CSP سخت و `X-Frame-Options: DENY`. احراز هویت دو مرحله‌ای نیست: اگر پنل روی اینترنت باز است، پشت احراز هویت یا فهرست IP مجاز پروکسی معکوس بگذارید.

## محدودیت‌های صادقانه

* اتصال `admin` عمداً قدرتمند است: نصب افزونه یا نوشتن فایل پوسته یعنی اجرای کد روی آن سایت. `admin` را کم و در نشست‌های زیرنظر بدهید و اگر هرگز نمی‌خواهید، سقف سایت را `live` بگذارید.
* rate limitها در حافظه‌ی یک پروسه‌ی gateway هستند.
* master key رمزهای سایت‌ها را رمز می‌کند؛ هر کس به `data/` و کلید دسترسی داشته باشد می‌تواند نقش gateway را پیش سایت‌ها بازی کند. آن پوشه را محافظت و بکاپ کنید.
* لاگ‌ها خلاصه‌ی کوتاه آرگومان دارند (نه محتوای کامل)، ممکن است عنوان یا slug صفحه در آن باشد.
* سئوی داخلی، ریدایرکت و CSS روی پوسته اعمال می‌شوند؛ افزونه‌های متعارض می‌توانند آن‌ها را بازنویسی کنند.
* افزونه بدون وردپرس واقعی تست واحد کامل نمی‌شود: مخزن تست‌های سیاست/امضا/پوشش spec دارد که بدون وردپرس اجرا می‌شوند و همه‌ی فایل‌ها را lint می‌کند؛ اولین اجرای واقعی را روی سایت آزمایشی (staging) انجام دهید.
