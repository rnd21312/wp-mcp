# نقشه‌ی راه: WP MCP Studio (نسخه‌ی ۲)

هدف: **ساخت هر نوع سایت از صفر، با هوش مصنوعی یا دستی، با یک راه‌اندازی ساده.** کاربر یک zip روی هاست معمولی‌اش می‌گذارد، در مرورگر بازش می‌کند، نام کاربری و رمز می‌گذارد و از آن به بعد از یک پنل روی کامپیوتر خودش سایت می‌سازد و مدیریت می‌کند.

این یک برنامه است، نه کد. بعد از جواب دادن به پرسش‌های آخر سند تغییر می‌کند.

## امروز چه داریم (نسخه‌ی ۱)

* gateway (Node) با سرور MCP و پنل محلی، و افزونه‌ی وردپرس («پل») با ۱۲۳ عملیات. سایت‌های **موجود** وردپرسی را مدیریت می‌کند: محتوا، طراحی، سئو، نگهداری، افزونه‌ها، فروشگاه، فایل‌ها، کپی بین سایت‌ها، ویرایشگر بصری، بازرس URL.
* آنچه برای هدف کم است: ساختن خود سایت (راه‌اندازی هاست، نصب وردپرس، تکنولوژی‌های غیر وردپرس)، build و استقرار پروژه‌های کدی، و یک جزء سمت هاست که به وردپرس وابسته نباشد.

## شکل نسخه‌ی ۲

```
 کامپیوتر شما                                   هاست شما (اشتراکی، VPS، هر چیز با PHP)
┌───────────────────────────────┐   HTTPS      ┌────────────────────────────────────┐
│ Studio (پنل محلی + MCP)       │  امضاشده     │ Host Agent (یک zip، PHP 8.1+)      │
│  فضای کار پروژه‌ها (git)      │ ───────────► │  نصب‌کننده · ورود (+۲FA) · API      │
│  سازنده‌ی AI، ویرایشگرها، پیش‌نمایش │ آپلود   │  releases/ + current · بازگشت       │
│  build محلی (npm, vite, …)    │ ◄─────────── │  نوع سایت: وردپرس · استاتیک ·       │
└───────────────────────────────┘  وضعیت       │  برنامه‌ی Node (اگر هاست اجازه دهد)  │
                                               └────────────────────────────────────┘
```

* **Host Agent**: یک برنامه‌ی کوچک PHP، چون PHP تنها چیزی است که هر هاست اشتراکی دارد. اجرای اول یک ویزارد است (بررسی نیازمندی‌ها، نام کاربری و رمز مدیر، TOTP اختیاری). API امضاشده‌ای شبیه همین پل دارد اما برای *پروژه‌ها* نه درون‌ساخت وردپرس.
* **Studio** (همین پنل گسترش‌یافته): روی کامپیوتر کاربر اجرا می‌شود، جایی که Node و npm و کلید AI می‌توانند باشند. هر پروژه را به‌صورت پوشه‌ی محلی زیر git نگه می‌دارد، پیش‌نمایش و build می‌کند و نتیجه را به Host Agent **می‌فرستد**. همه‌ی اتصال‌ها از کامپیوتر به بیرون است، پس تنظیم مودم یا فایروال لازم نیست.
* **Releaseها**: هر استقرار یک پوشه‌ی تغییرناپذیر به‌علاوه‌ی سوییچ اتمی است، با بکاپ خودکار و بازگشت یک‌کلیکی.

## نوع سایت‌ها و نحوه‌ی تحویل

| نوع | کجا ساخته می‌شود | تحویل | نکته |
|---|---|---|---|
| وردپرس | Host Agent آن را فراهم می‌کند (دانلود هسته، تنظیمات، نصب، فعال‌سازی پل، جفت‌سازی خودکار) | نصب زنده | دیتابیس لازم دارد؛ agent مشخصات را می‌پرسد یا اگر هاست API دارد (cPanel UAPI) خودش می‌سازد |
| استاتیک (HTML/CSS/JS، Astro، Eleventy) | محلی | فایل‌ها | روی هر هاستی کار می‌کند |
| React / Vue / Svelte (Vite) | محلی (`npm run build`) | فایل‌های استاتیک + قواعد بازنویسی SPA | روی هر هاستی |
| Next.js / Nuxt | محلی | به‌طور پیش‌فرض **خروجی استاتیک**؛ SSR فقط اگر هاست Node داشته باشد (Node app در cPanel، Passenger) یا VPS باشد | agent گزارش می‌دهد هاست چه می‌پذیرد و Studio مقصد را انتخاب می‌کند |
| برنامه‌های PHP، Laravel | محلی | فایل‌ها + composer روی هاست در صورت اجازه | بعداً |

## سازنده‌ی هوش مصنوعی

ابزارهای MCP جدید و جریان‌های پنل روی ابزارهای فعلی:

۱. `project.create {type, brief}`، `project.list`، `project.open`.
۲. `workspace.*`: خواندن، نوشتن، فهرست، جستجو، اجرای فرمان فقط داخل پوشه‌ی پروژه.
۳. `build.run`، `preview.start/stop` (سرور توسعه‌ی محلی در ویرایشگر بصری پنل نشان داده می‌شود).
۴. `deploy.push {host, project}`، `deploy.releases`، `deploy.rollback`، `host.status`.
۵. یک مسیر هدایت‌شده با **ایست‌بازرسی‌هایی که انسان تأیید می‌کند**: شرح کسب‌وکار ← نقشه‌ی سایت و صفحات ← سیستم طراحی (توکن‌ها، کامپوننت‌ها) ← ساخت صفحات ← محتوا و تصاویر ← سئو ← ممیزی سرعت و دسترس‌پذیری ← استقرار. در هر گام AI پیشنهاد می‌دهد، کاربر در پنل تأیید یا ویرایش می‌کند و بعد ادامه می‌دهد.
۶. ویرایشگر بصری و بازرس URL فعلی روی هر نوع پروژه کار می‌کنند، نه فقط وردپرس.

## مدل امنیتی Host Agent

* نام کاربری و رمز (scrypt)، TOTP اختیاری، قفل در برابر حدس رمز، توکن راه‌اندازی در اجرای اول، HTTPS اجباری.
* درخواست‌های امضاشده با secret جدا برای هر اتصال (همان طرح HMAC پل)، ضد replay، دامنه‌ی دسترسی برای هر پروژه.
* عملیات فایل محدود به پوشه‌ی پروژه؛ آپلود zip + هش، راستی‌آزمایی و بازکردن در release تازه؛ بدون اجرای فرمان دلخواه روی هاست؛ فایل PHP در release فقط از artifact خود کاربر.
* لاگ ممیزی، بکاپ پیش از هر استقرار، بازگشت.
* به‌روزرسانی امضاشده‌ی خود agent.

## ریسک‌های اصلی

* هاست‌های اشتراکی خیلی متفاوت‌اند (توابع بسته، PHP قدیمی، دسترسی فایل، cPanel در برابر DirectAdmin). باید زود ماتریس آزمون با هاست‌های واقعی داشت.
* «هر استک» گسترده است؛ هر قالب نگهداری واقعی می‌خواهد. با چهار قالب شروع کنیم و افزودن قالب را ارزان کنیم.
* agentی که استقرار می‌پذیرد هدف باارزشی است؛ مدل امنیتی بالا باید اول ساخته شود نه آخر.
* رندر سمت سرور Next.js/Nuxt روی هاست اشتراکی ساده ممکن نیست؛ باید روشن به کاربر گفت.

## پرسش‌هایی که طرح را تعیین می‌کنند

۱. کاربران شما چه هاستی دارند: cPanel، DirectAdmin، Plesk، هاست‌های ایرانی، VPS؟ Node روی آن‌ها هست؟
۲. SSR در Next.js ضروری است یا برای نسخه‌ی اول خروجی استاتیک کافی است؟
۳. چه کسی استفاده می‌کند: آژانس‌هایی که برای مشتری می‌سازند یا کاربران نهایی که سایت خودشان را می‌سازند؟
۴. Studio همچنان برنامه‌ی محلی بماند یا بعداً سرویس میزبانی‌شده هم باشد؟
۵. متن‌باز، پولی، یا هر دو؟ روی بازارچه‌ی قالب و به‌روزرسانی‌ها اثر دارد.
