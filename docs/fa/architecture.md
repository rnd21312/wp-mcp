# معماری

## تصمیم: gateway مرکزی + افزونه‌ی سبک وردپرس

دو شکل ممکن بود:

| | فقط افزونه (یک endpoint MCP داخل هر سایت) | **gateway + افزونه (انتخاب‌شده)** |
|---|---|---|
| چند سایت | برای هر سایت یک connector جدا در Claude؛ هوش مصنوعی باید چند سرور را مدیریت کند | یک connector؛ هر ابزار `site` می‌گیرد و نتیجه نام سایت را تکرار می‌کند |
| ورود پایدار | توکن‌ها در `wp_options` هر سایت‌اند؛ قفل/کش گزینه، مهاجرت یا افزونه‌ی امنیتی می‌تواند آن‌ها را از بین ببرد | توکن‌ها در SQLite خود gateway‌اند، مستقل از سایت‌ها؛ از دسترس خارج شدن یا نصب مجدد سایت، ورود را نمی‌پراند |
| سرور OAuth | روی هر سایت عمومی دوباره پیاده و در معرض اینترنت (سطح حمله بیشتر، rate limit مشترک با endpoint توکن) | یک پیاده‌سازی مقاوم، با سطل‌های rate limit جدا |
| بررسی‌های ایمنی | پخش در چند سایت که هرکدام باید به‌روز شوند | سطح‌ها، تأییدها، محافظ SSRF و لاگ در یک جا؛ افزونه دوباره اعمال می‌کند (دفاع چندلایه) |
| هزینه | چیزی برای میزبانی نیست | یک سرویس کوچک Node برای میزبانی (Docker یا یک پروسه) |

هزینه واقعی است، سود هم واقعی است؛ پس gateway برنده شد. افزونه عمداً کوچک مانده: یک endpoint امضاشده، فهرستی از handlerها و تا زمانی که gateway جفت نشود هیچ.

## اجزا

```
spec/build-spec.mjs ──► spec/ops.json ──► gateway/src/generated/ops.json
                                      └─► plugin/wp-mcp-bridge/ops.json
```

`ops.json` تنها تعریف ۱۱۷ عملیات سایت است: کمترین سطح، آرگومان‌ها، نوشتن بودن، نیاز به تأیید و اینکه نتیجه متن سایت دارد یا نه. اگر کپی‌ها فرق کنند یک تست و اگر عملیاتی handler نداشته باشد (یا برعکس) یک تست PHP شکست می‌خورد.

### gateway (پوشه `gateway/`، TypeScript، Node ≥ 22.13، بدون وابستگی زمان اجرا)

| فایل | کار |
|---|---|
| `http.ts` | مسیریابی، محدودیت بدنه، CORS، `/mcp` (فقط POST، بدون حالت) |
| `mcp/server.ts` | JSON-RPC: initialize (با `instructions`)، ابزارها، منابع، promptها |
| `mcp/tools.ts` | مراحل یک فراخوانی ابزار (پایین) |
| `mcp/guide.ts` | instructions، منابع راهنما، promptها |
| `registry.ts` | ابزارها و عملیات از spec، اعتبارسنجی و تبدیل نرم آرگومان‌ها |
| `oauth.ts` | OAuth 2.1: کشف، ثبت پویا، authorize/رضایت، توکن، ابطال |
| `auth.ts` | توکن Bearer و کلید API ← یک *principal* (سطح، سایت‌ها) |
| `wpclient.ts` | فراخوانی امضاشده به افزونه، retry، راستی‌آزمایی پاسخ |
| `ssrf.ts` | HTTP محافظت‌شده: DNS در لحظه‌ی اتصال بررسی می‌شود، بدون redirect، سقف حجم |
| `store.ts` | SQLite (`node:sqlite`): سایت‌ها، کلیدها، کلاینت‌ها، grantها، توکن‌ها، فعالیت، idempotency |
| `admin.ts` | پنل مالک: سایت‌ها، کلیدها، اپ‌ها، فعالیت |

### افزونه (پوشه `plugin/wp-mcp-bridge/`، PHP ≥ 8.1)

| فایل | کار |
|---|---|
| `Api.php` | `/wp-json/wp-mcp/v1/{call,pair,ping}`؛ تأیید امضا، مجوز، اجرا، لاگ، امضای پاسخ |
| `Signature.php`، `Connections.php` | امضای HMAC؛ کد جفت‌سازی یک‌بارمصرف؛ secret و سقف سطح هر اتصال |
| `Policy.php` | قواعد خالص: ردهٔ گزینه‌ها، پنهان‌سازی رمزها، سطح مسیرهای REST، بررسی URL/SSRF، مسیر فایل‌های پوسته |
| `Revisions.php`، `Activity.php` | snapshot برای undo و لاگ سمت سایت (دو جدول کوچک) |
| `Frontend.php` | اثر عمومی تنظیمات: CSS، توکن‌ها، ریدایرکت، سئوی داخلی، robots.txt، حالت تعمیر |
| `Handlers/*.php` | یک کلاس برای هر ابزار: `op_<action>` (و در صورت نیاز `preview_<action>`) |

## مراحل یک فراخوانی ابزار

۱. `POST /mcp` با `Authorization: Bearer …` ← principal (کلید API یا توکن OAuth که با grant *فعلی* مالک سنجیده می‌شود، پس تغییرات فوراً اعمال می‌شود).
۲. اعتبارسنجی `action` و `args` با spec (آرگومان ناشناخته یا بدنوع خطای دقیق با signature می‌گیرد).
۳. انتخاب سایت (اگر principal به بیش از یک سایت دسترسی دارد `site` الزامی است). **سطح مؤثر** = `min(سطح principal، سقف سایت)`؛ کمتر از سطح عملیات = رد.
۴. rate limit: برای هر اتصال، برای نوشتنِ هر اتصال، و برای هر سایت.
۵. تأیید: عملیات `confirm` یک `needs_confirmation` با پیش‌نمایش (همان `dry_run` افزونه) و یک `confirm_token` وابسته به principal، سایت، عملیات و همان آرگومان‌ها برمی‌گردانند. عملیات `maybe` (REST عمومی، options) را افزونه از روی آرگومان‌ها تعیین می‌کند.
۶. Idempotency: `idempotency_key` کلاینت نتیجه‌ی ذخیره‌شده را بازپخش می‌کند؛ gateway همیشه یک کلید به افزونه می‌فرستد تا retryِ انتقال هرگز دوبار ننویسد.
۷. `POST` امضاشده به افزونه: `HMAC-SHA256(secret, زمان، nonce، شناسه کلید، مسیر، sha256(بدنه))`، پنجره‌ی ۵ دقیقه، حافظه‌ی ضد replay. افزونه مدیر عامل را تنظیم می‌کند، سطح را دوباره می‌سنجد (و از روی هدف واقعی بالا می‌برد: ویرایش نوشته‌ی *منتشرشده* `live` می‌خواهد حتی اگر ذخیره‌ی پیش‌نویس `draft` بخواهد)، snapshot برای undo ثبت می‌کند، handler را اجرا و پاسخ را امضا می‌کند؛ gateway پاسخ بدون امضا را رد می‌کند.
۸. gateway فراخوانی را لاگ می‌کند و `{ok, site, action, revision?, data, content_notice?}` برمی‌گرداند.

## پایداری اتصال

* توکن دسترسی OAuth: ۱ ساعت. Refresh token: **۱۸۰ روز، لغزان و چرخشی**. تکرار refreshی که پاسخش گم شده جواب داده می‌شود (۱۰ دقیقه مهلت)؛ بازپخش refresh قدیمی بعد از آن، زنجیره را می‌بندد.
* refresh با grant فعلی مالک سنجیده می‌شود؛ پایین آوردن سطح یا قطع اپ از فراخوانی بعدی اثر می‌کند.
* هیچ session حالت‌داری برای MCP نیست: هر نمونه‌ی gateway می‌تواند هر درخواست را جواب دهد و کلاینت می‌تواند آزادانه قطع و وصل شود.
* کلید API منقضی نمی‌شود مگر تاریخ انقضا بگذارید.

## محدودیت‌های شناخته‌شده

* هر gateway یک مالک دارد؛ rate limit در حافظه است (یک پروسه).
* افزونه همه‌چیز را نمی‌تواند snapshot کند (حذف افزونه، پاکسازی دیتابیس، به‌روزرسانی‌ها و حذف‌های دائمی undo ندارند؛ `maintain.update` قبلش بکاپ دیتابیس می‌گیرد).
* سایت‌ها باید از gateway با HTTPS در دسترس باشند.
